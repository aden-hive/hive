Session audit: session_20260508_102516_c8fd6fa7

An audit of one real production session whose compaction output looks structurally damaging. Each finding is backed by the actual file on disk plus the exact source line that produces the behavior. Five distinct problem classes identified.

Status — 2026-05-12: Direction A applied
Direction A from Section 9 was acted on: the structure-preserving compaction stage was removed from the pipeline. Specifically —
  • The Stage 2 call was removed from the orchestrator (compaction.py); the pipeline is now Stage 0 microcompact → Stage 1 prune → Stage 2 LLM summary → Stage 3 emergency.
  • NodeConversation.compact_preserving_structure and the _compact_tool_calls / _TC_ARG_LIMIT helper + constant were deleted from conversation.py.
  • The seven tests in TestAggressiveStructuralCompaction and the _build_tool_heavy_conversation helper were removed from test_node_conversation.py. The remaining 102 conversation tests pass.
  • The descriptive pages of this docset (Overview, Pipeline, Transformations, Configuration) were updated to reflect the new four-stage pipeline. This audit page is preserved verbatim below as the historical record that motivated the change.
Existing on-disk session data that predates this change — including the session under audit here — still contains the {"_compacted": "…"} sentinels and the conversation_N.md spillover chain documented below. Newly compacted sessions do not produce either.
Bottom line
96 of 614 conversation parts (15.6%) have their tool-call arguments destroyed by the 200-character cap in _compact_tool_calls(). The session has cascaded through four successive structural compactions, each writing a new conversation_N.md that only references the previous one. At least one tool call (excel_write at seq 69) has been compacted twice, showing the wrapper is not idempotent. Content-bearing tools (write_file, terminal_exec with heredocs, excel_write, chart_render) lose their payloads — the agent can no longer audit or replay what it did.

2. The 200-character tool-call argument cap

All 96 destroyed arguments share the same root cause: the constant _TC_ARG_LIMIT = 200 inside _compact_tool_calls().

core/framework/agent_loop/conversation.py:210-258 
_TC_ARG_LIMIT = 200  # max chars per tool_call argument after compaction


def _compact_tool_calls(tool_calls: list[dict[str, Any]]) -> list[dict[str, Any]]:
    """Truncate tool_call arguments to save context tokens during compaction.

    Preserves ``id``, ``type``, and ``function.name`` exactly.  When arguments
    exceed ``_TC_ARG_LIMIT``, replaces the full JSON string with a compact
    **valid** JSON summary.
    """
    compact = []
    for tc in tool_calls:
        func = tc.get("function", {})
        args = func.get("arguments", "")
        if len(args) > _TC_ARG_LIMIT:                                  # <-- the trigger
            try:
                parsed = json.loads(args)
                if isinstance(parsed, dict):
                    summary_parts = []
                    for k, v in parsed.items():
                        v_str = str(v)
                        if len(v_str) > 60:                                # <-- inner per-value cap
                            v_str = v_str[:60] + "..."
                        summary_parts.append(f"{k}={v_str}")
                    summary = ", ".join(summary_parts)
                    if len(summary) > _TC_ARG_LIMIT:
                        summary = summary[:_TC_ARG_LIMIT] + "..."     # <-- outer cap again
                    args = json.dumps({"_compacted": summary})

So an argument like chart_render(spec=<5 KB JSON>) survives as "spec={\"title\": {\"text\": \"ISRG vs TEM vs OSCR— 1-Year Per..." — the first 60 chars of the value, repeat for the next key, total capped at 200. For content-bearing tools this is unrecoverable destruction.

Look closely: the value starts with _compacted=path=…
The leading _compacted= inside the value means the wrapper sees an already-compacted argument string and wraps it a second time. After the first compaction the args were {"_compacted": "path=ISRG_DCF_Model.xlsx, columns=…"}. On the second pass, the loader parsed that into {"_compacted": "path=…"}, walked the dict, emitted "_compacted=path=…" as a key=value pair, and re-wrapped. Section 3 below digs into the idempotency bug.

3. The double-compaction idempotency bug

The wrapper at conversation.py:213-258 decides whether to compact purely from len(args) > _TC_ARG_LIMIT. There is no check for an existing {"_compacted": "…"} envelope, so each successive structural-compaction pass that runs against the same message wraps the args again.

The excel_write at seq 69 is the smoking gun: 

# After first compaction:
{"_compacted": "path=ISRG_DCF_Model.xlsx, columns=['Sheet', 'Section', 'Line', 'Value'...]"}

# After second compaction (this is what's on disk):
{"_compacted": "_compacted=path=ISRG_DCF_Model.xlsx, columns=['Sheet', 'Section', 'Line..."}
#               ^^^^^^^^^^^                                                                ^^^
#               The PREVIOUS sentinel got walked as a dict key on the second pass.            Truncated again,
#               losing the tail.

After N successive compactions a content-bearing tool call has N envelopes of sentinel wrapper around what is now a 60-character glimpse of the original. With this session at four compactions deep, anything compacted on pass 1 is also two-deep wrapped if it survived past pass 2’s keep_recent boundary.

Every structural compaction allocates a fresh file. The new file’s contents are drawn from the current live conversation, which already starts with the previous compaction’s reference message at seq 0. The reference is included as-is in the new spill file, producing the chain. The injected reference message in the new live conversation only mentions the latest file. There is no merge step, no dereferencing, no flattening.

7. Root-cause summary

  1. _TC_ARG_LIMIT = 200 is too small for content-bearing tool calls. conversation.py:210. A 200-char outer cap with a 60-char per-value cap loses the entirety of any meaningful argument body: file content, command body, chart spec, batch payload.
  2. _compact_tool_calls() is not idempotent. conversation.py:213-258. The trigger is purely len(args) > _TC_ARG_LIMIT; there is no check for an existing {"_compacted": "…"} envelope, so each pass re-wraps. Cause of the seq-69 double envelope.
  3. Structural compaction runs _compact_tool_calls() indiscriminately on every old assistant message. conversation.py:1439-1452. Tool semantics are ignored: read_file args (cheap to drop) and write_file args (irreplaceable) are treated identically.
  4. Spillover files form a linked chain, not a flat archive. conversation.py:1464-1472. The new ref message only points at the latest file. Older files are reachable only by following the chain, and each read_file on the chain adds to the current context budget.
  5. The keep_recent boundary is too tight for sessions with bursty tool use. keep_recent=4 at compaction.py:297-304. Anything older than four messages at the moment of the trigger loses its arguments, including very recent content-bearing calls.

8. Suggested follow-up work (not executed)

Direction, not implementation
These are observations for the maintainers of the compaction pipeline. None of them are applied by this audit.
  • Per-tool retention policy. Declare a small set of fields as “content-bearing” (e.g. write_file.content, excel_write.data, terminal_exec.command, chart_render.spec). Either keep them full-fidelity, or spill them to a separate file and reference the path, rather than truncating to 200 chars.
  • Idempotency in _compact_tool_calls(). Before wrapping, check whether the parsed dict already has a single _compacted key — if so, leave it alone. Prevents the seq-69 double-wrap pathology.
  • Flatten the spillover chain. Either append to a single conversation.md, or carry the original head reference forward when a new file is created, so the “Previous conversation saved at: …” in the live conversation always points at the first file in the chain (and an index of subsequent files listed for cheap traversal).
  • Tune _TC_ARG_LIMIT upward or remove it for content-bearing tools. The token savings at 200 chars are marginal (a single chart_render spec is ~3 KB, so capping at 1–2 KB still saves most of the bytes while keeping useful detail).
  • Don’t empty content on kept structural messages. The current code clears content when rewriting an assistant tool-call message (conversation.py:1414), which loses any “thinking” prose the model emitted alongside the tool calls.

9. Is structure-preserving compaction salvageable at all?

The deeper question
The fixes in sections 7–8 treat the symptoms. The harder question is whether Stage 2 — “preserve tool-call structure, spill freeform text to a file” — can be made to work, or whether the design itself is the bug.

What Stage 2 claims to do

core/framework/agent_loop/conversation.py:1304-1320 
"""Structure-preserving compaction: save freeform text to file, keep tool messages.

Unlike ``compact()`` which replaces ALL old messages with a single LLM
summary, this method preserves the tool call structure (assistant
messages with tool_calls + tool result messages) that are already tiny
after pruning.  Only freeform text exchanges (user messages,
text-only assistant messages) are saved to a file and removed.

...

The result: the agent retains exact knowledge of what tools it called,
where each result is stored, and can load the conversation text if
needed.  No LLM summary call.  No heuristics.  Nothing lost.
"""

Three claims are doing the work here: (a) tool-call pairs are tiny after pruning; (b) the agent retains exact knowledge of what it called; (c) nothing is lost. Looking at the actual on-disk state of this session, none of the three survive contact with reality.

Claim audit (with disk evidence from this session)

Claim from the docstring What this session shows
Tool-call pairs are tiny after pruning. Prune touches tool results only (conversation.py:1082: if msg.role != "tool": continue). The assistant messages with their full tool-call arguments — a 5 KB chart_render spec, a 2 KB Python heredoc, a write_file with the entire file body — are not touched by Stage 1. So when Stage 2 runs, the args are still large and Stage 2’s only tool is the 200-char truncation. The premise is false for content-bearing sessions.
The agent retains exact knowledge of what tools it called. 96 parts in this session disagree. The agent knows tool names (preserved) but not arguments (truncated to 60 chars per field, total 200). For terminal_exec the command body is the call; for write_file the content is the call; for chart_render the spec is the call. Names without args are not knowledge.
Nothing is lost. Lost in this session: the original user prompt (now four files away), 96 tool-call argument bodies, an unknown number of assistant “thinking” prose strings (wiped to content="" at conversation.py:1414), and one tool call that was double-wrapped past readability (seq 69).

The spill-to-file pattern in particular

The user’s focus is right: the bit that writes to a file is where the damage compounds. Let’s walk through what actually happens.

What is in each file?

FileSizeWhat it contains
conversation_1.md128 BThe original user prompt (one line: “chart isrg vs tem vs oscr stocks”) plus the ## Compacted conversation header.
conversation_2.md2.4 KBOne injected reference to conversation_1.md at the top, then ~40 freeform messages from messages 12–51.
conversation_3.md17 KBReference to conversation_2.md at the top, then ~280 freeform messages from 52–330. This is the bulk of the freeform conversation.
conversation_4.md11 KBReference to conversation_3.md at the top, then freeform messages from 331–521.

Total: ~30 KB across four files, none of which can stand alone. To answer “what did the user originally ask?” the agent must call read_file four times in sequence, each time loading more content into the live context until eventually it triggers yet another compaction.

The retrieval pathology

Each recovery read costs more than the bytes recovered
Reading conversation_4.md (11 KB) into context to satisfy the reference message in part 0 immediately consumes ~3,000 tokens. The result contains another reference to conversation_3.md — another read. After all four reads the agent has consumed ~10,000 tokens of context just to recover the same freeform conversation that compaction was supposed to save space on. The agent has now likely tripped the next compaction threshold, which will write conversation_5.md and the cycle repeats — with the inflated chain inside it.

What “append” would look like

Looking at conversation.py:1464-1486, the spill writes only the messages between the previous compaction’s boundary and the current one. The previous compaction’s ref message is included in “old freeform” and gets serialised right back into the new file. Each file is therefore a slice plus the head of the previous slice — a linked list, not a transcript. An honest implementation would either:

  • Open conversation_1.md in append mode each time, producing one growing transcript and a single ref message that always points at it; or
  • Dereference the previous-compaction ref before spilling, so each file is self-contained for its slice; or
  • Carry forward an explicit “original head” reference inside every new file so the chain is one-deep at most.

Three possible directions, evaluated

Direction A — remove Stage 2 entirely

When Stage 0 microcompact and Stage 1 prune together aren’t enough, skip straight to Stage 3 LLM summary. Stage 4 emergency remains as the last resort.

ProCon
One coherent summary file instead of a chain of partial transcripts. No more _compacted args, no more idempotency bug, no more “recent isn’t safe”. Every above-Stage-1 compaction costs an LLM call (latency + tokens). On a session with 4 compactions like this one, that’s 4 extra calls.
The LLM summary’s structured-sections prompt (compaction.py:626-656) already carves out “User Messages preserved verbatim” and “Files and Code Sections” — the things Stage 2 currently destroys. The agent loses the “structural” affordance of being able to see exactly which tool calls happened. But the current implementation only preserves names anyway, which the LLM summary’s tool-history block at compaction.py:512-516 already captures.
Removes the file-chain pathology entirely. Spillover dir is no longer load-bearing. Circuit-breaker on LLM failures becomes more important — without Stage 2 to fall back to, three failed LLM compactions go straight to Stage 4 emergency.

Direction B — keep Stage 2 but spill, don’t truncate

Treat tool-call argument bodies the way truncate_tool_result treats tool-result content: if they’re long, write them to disk and replace the in-message value with a path reference and a length annotation.

ProCon
Preserves the “free, no LLM” cost profile. Doubles down on the spill-to-file pattern that already hurts retrieval in this session. More files to chase, not fewer.
Fixes the “Nothing lost” claim — an agent can always read_file the spilled args. Each spilled arg is now a separate file. A session with 70 chart_render calls produces 70 extra files in the data dir. Operational mess.
No LLM dependency, no token cost. Doesn’t solve the conversation_N.md cascade; the freeform-text chain is independent and remains.

Direction C — merge Stage 1 and Stage 2, drop the “structure” abstraction

Have Stage 1 prune both tool results and oversized tool-call arguments. Stage 2 becomes “move freeform text to a single appending transcript file” only — no truncation of tool calls.

ProCon
The conceptual model becomes clearer: prune handles content, freeform spill handles prose. No more “destroy by 200-char cap” step. Requires touching the prune logic at conversation.py:1044-1145 to also walk old assistant tool_calls.
The transcript file becomes a single append-only artefact; the cascade goes away. Still doesn’t answer “why preserve the structure at all?” if the args are mostly path-references after pruning.

Recommended posture

The evidence in this session supports a stronger conclusion than the section-8 list: Stage 2 as currently designed is doing net harm. The “free” appellation is misleading because the retrieval cost (each recovery read consumes budget) plus the fidelity loss (96 destroyed args, double-wrapping, content wipe) outweigh the avoided LLM call. Direction A (remove Stage 2) is the cleanest position to defend on this evidence; Direction C is a reasonable conservative alternative if losing the “no LLM in the cheap path” property is unacceptable. Direction B addresses the worst symptom but keeps the structural problem.

Caveat on generalisation
This audit is one session. The session is content-bearing (charts, files, batches) and that is exactly the failure mode Stage 2 handles worst. A session whose tool results dominate (e.g. mostly read_file + web_scrape with short calls) may genuinely benefit from Stage 2. Before ripping it out, a similar audit on a non-content-bearing session would be worth running; the framework already collects the inventory needed for that (build_message_inventory + HIVE_COMPACTION_DEBUG dumps it to disk).
