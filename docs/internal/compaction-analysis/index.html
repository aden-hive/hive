Compaction Pipeline Analysis

How the hive-desktop-runtime agent loop keeps a conversation inside the model’s context window: when compaction fires, the four-stage pipeline that runs, what gets discarded versus preserved, and every knob that controls the behavior.

About the _compacted sentinel (historical)
Older docs and existing on-disk session data may show tool calls whose arguments look like {"_compacted": "key1=val1, key2=val2..."}. That was produced by a helper called _compact_tool_calls() as part of the structure-preserving stage. Both the helper and the stage were removed on 2026-05-12 (see Audit). The sentinel may still appear in archived session parts but is no longer generated by new compactions.

Why compaction exists

Hive agents accumulate context aggressively: tool results from read_file, web_scrape, browser_snapshot, terminal output, and screenshots can each add tens of thousands of characters to a conversation. Without intervention, the next LLM call would either bust the model’s context window (HTTP 400 from the provider) or pay for tokens that no longer carry useful information. Compaction is the runtime’s answer to that: a layered, cost-ordered strategy that trims, prunes, spills to disk, and finally summarizes — always trying the cheapest option first and short-circuiting as soon as the budget is restored.

One-paragraph overview

Four checkpoints in the agent loop ask conversation.needs_compaction() whether compaction should fire (pre-turn, post-turn, pre-send, and proactively after every tool result). When triggered, the orchestrator at internals/compaction.py:204 runs a four-stage pipeline: Stage 0 microcompaction (count-based, free, synchronous), Stage 1 prune (token-budget, free), Stage 2 LLM summary (paid, recursive binary split), Stage 3 emergency deterministic summary (fallback if LLM unavailable or has failed too many times). Each stage rechecks needs_compaction() and exits early once headroom is restored. The trigger uses a hybrid “fixed tokens + ratio of window” budget so the same parameters scale across 32k and 1M-token windows.

2026-05-12 update
The pipeline was previously a five-stage design that included a free, no-LLM “structure-preserving compaction” between prune and LLM summary. It was removed after the audit on this page revealed it was doing net harm: a 200-char tool-call argument cap that destroyed content-bearing calls, a non-idempotent wrapper that double-wrapped on repeat passes, and a linked chain of spillover files that made history recovery cost more than the LLM call it avoided. See Audit for the full case.

Glossary

TermMeaning
needs_compaction() The instance method on NodeConversation that returns True when the conversation has crossed the compaction budget. Hybrid buffer model. conversation.py:969-997
Microcompaction Stage 0. The cheapest form of compaction: count-based replacement of old tool results with a short placeholder. Synchronous, no LLM, no store writes. Fires both proactively on every tool result and as the first stage of the full pipeline. compaction.py:91-161
Prune Stage 1. Token-budget-aware replacement of old tool result content with a placeholder that includes the spillover path for recovery. conversation.py:1044-1145
Structure-preserving compaction Removed 2026-05-12. Was a no-LLM stage between prune and LLM summary; saved freeform text to numbered conversation_N.md files and applied a 200-char cap to tool-call arguments. Removed because the cap destroyed content-bearing calls and the file chain inflated retrieval cost. See Audit.
LLM compaction Stage 2. Calls the configured LLM to produce a structured prose summary of the old messages. Recursive binary split when the formatted input exceeds 240k chars or the API rejects on context length. compaction.py:412-518
Emergency summary Stage 3. Deterministic fallback that builds a summary from node identity, inputs, output accumulator state, and spillover file listing — no LLM call. Used when the LLM is unavailable or the circuit breaker has tripped. compaction.py:831-921
Spillover The pattern of writing large content to disk and replacing the in-context copy with a reference. Used by tool result truncation and prune placeholders. The reference always carries the full path so the agent can read_file() or terminal_rg on demand.
Phase / transition marker Hive’s continuous-mode notion of a logical work phase. Messages carry phase_id; transition markers (is_transition_marker=True) sit at phase boundaries. The current phase is never pruned; transition markers are never pruned at any level.
Skill content Messages flagged is_skill_content=True carry activated SKILL.md instructions. Protected at every level (AS-10 invariant) so an activated skill is never lost to compaction mid-task.
Output keys / accumulator A node’s declared outputs (spec.output_keys) and the running OutputAccumulator that holds set values. Compaction extracts already-set values from discarded messages and re-injects them under a PRESERVED VALUES heading.
COMPACTABLE_TOOLS The frozenset of tool names whose results are safe to clear: their content is re-derivable (re-read the file, re-run the search, re-capture the screenshot). compaction.py:39-66

Top-level orchestrator at a glance

core/framework/agent_loop/internals/compaction.py:204-222 
async def compact(
    ctx: NodeContext,
    conversation: NodeConversation,
    accumulator: OutputAccumulator | None,
    *,
    config: LoopConfig,
    event_bus: EventBus | None,
    char_limit: int = LLM_COMPACT_CHAR_LIMIT,
    max_depth: int = LLM_COMPACT_MAX_DEPTH,
) -> None:
    """Run the full compaction pipeline if conversation needs compaction.

    Pipeline stages (in order, short-circuits when budget is restored):
    0. Microcompaction (count-based tool result clearing — cheapest)
    1. Prune old tool results (token-budget based)
    2. Structure-preserving compaction (free, no LLM)
    3. LLM summary compaction (recursive split if too large)
    4. Emergency deterministic summary (fallback)
    """
